# 四路相机实机测试 · 2026-10-12

测试目标 `192.168.10.10:60000`，本机 `192.168.10.100:60000`。本轮按用户要求跳过心跳，所有设备操作通过 C++ SDK 完成，接收严格校验内外两层 CRC。未使用 UDP 模拟器。

## 寄存器读写

CAM 1～4 每路测试以下四个寄存器，共 **16/16 通过**。流程为读取原值、写入小幅不同的测试值、回读比较、恢复原值、再次回读确认。

- `0x0001` 曝光：5000 → 5001 → 5000 μs。
- `0x0002` 增益：0 → 1 → 0。
- `0x000D` 行间距：4500 → 4501 → 4500。
- `0x0011` 帧等待：1000 → 1001 → 1000。

32 次写入（16 次测试及 16 次恢复）均收到 `0000` ACK，48 次读取均匹配预期。四路原值一致，所有恢复均经回读确认。ROI 的 READ 在 Python 实现中注明设备不应答，因此未做无法保存原值的 ROI 写入。未改动网络、供电、激光开关、序列号、标定、测试模式或固件。

原值和全部请求/应答明细保存在项目目录 `out/sdk-v2-hardware-rw-20261012-164838/` 的 `original_registers.tsv`、`transactions.tsv`、`summary.json`。

## 0x0300 图像获取

四路 `Data=0000` 各连续请求三次，12/12 正常回应 `Cmd=0300`。另每路请求一次 `Data=0001`，4/4 也收到图像，但仍回应 `Cmd=0300`，没有按协议切换为 `Cmd=0301`。

**首次共 16/16 图像获取和解码成功**；请求模式协议符合性为 12/16。四路图像均为 Gray8、2048×1080。首次测试收包 35,112，CRC/帧格式异常、组包缺失、请求超时均为零。中心线和点云均各有 2048 点；CAM2 的插值块 count 为 0，其他相机为 1600。

离线对照八个首帧：C++ 与原 Python 的图像、中心线、点云、插值全部值一致，四类数据块均完整且长度/count 对应。本次固件的块 Length 为 body 长度，不含 Length 自身 4B；SDK 两种口径的兼容解析生效。

但固件的排列声明错误：`Cmd=0300、Format=1` 标为标准排列，实际像素仍是 FPGA lane 原始交织布局。按声明显示周期虚线，显式原始重排后恢复连续的真实线段。Python Auto 和 SDK Auto 因暗画面亮列不足没有自动纠正，因此本次兼容方式是显式 `ImageLayout::FpgaRaw`，不修改设备或原始应答。

采用 SDK 新的逐相机布局覆盖接口，再次进行 **8/8 实机图像获取/重排**，收包 17,516，CRC/组包/超时/队列丢弃均为零。文件位于 `out/sdk-v2-hardware-images-20261012-165719/`；`Data=0001` 的模式不符仍单独记为协议问题，没有伪装成切换成功。

## 连续四路采集与 Qt

实机转发板同时处理四个图像请求时没有返回完整图像。SDK 默认采集策略已调整为整个转发板最多一帧在途，按相机轮询；具备并行能力的其它固件可显式设置并发上限。

调整后进行 5 秒实机连续采集，稳定快照记录为 CAM1 35 帧、CAM2～4 各 34 帧，合计 **137 帧**。收包 302,160、接收字节 316,559,514；CRC/格式异常、组包缺失、请求超时、解码队列丢弃全部为零。该验证为短时间功能测试，不代表长期稳定性或最大带宽测试。

连续测试明细和末帧位于 `out/sdk-v2-hardware-continuous-20261012-170921/`。Qt demo 已支持“跳过心跳”及独立图像解码选项，实机四路预览成功退出 0，截图保存在图像复验目录。新增布局覆盖与共享转发板并发限制回归后，**14/14 CTest 通过**。

当前固件待修正点：让 `Data=0000/0001` 与返回 `Cmd/Format`、实际像素排列保持一致；并明确转发板对多图像事务的并发能力。SDK 已提供串行轮询和显式重排作为当前设备的兼容运行方式。
